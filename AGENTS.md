# Collaboration Rules — Professional Hello World

## Learning Goals

This artistic and humorous project also serves as a learning environment. Its deliberately disproportionate technical challenges give Vincent opportunities to discover and practice new techniques, including WebGL when that topic is explored together.

## Code: Propose in the Conversation, Let Vincent Make the Changes

- Present proposed code in the conversation, identifying the relevant file and where to insert or replace it.
- Explain how it works and the choices that support learning, at a pace suited to Vincent's questions.
- Do not directly create, modify, delete, rename, or reformat code files, even for minor fixes.
- This rule includes scripts, tests, shaders, HTML, CSS, JavaScript, TypeScript, Python, as well as technical configuration, dependencies, and workflows.
- Do not apply patches or run tools that generate or modify these files. Vincent applies the proposed changes himself.
- Reading and analyzing code is allowed. Any verification must preserve this no-modification rule.
- A general request to implement or fix something does not override this rule: present the code in the conversation. Only explicit authorization from Vincent to edit code directly permits an exception, within the scope he specifies.

## Documentation: Direct Editing Is Allowed

- The assistant may directly create and edit prose documentation, especially `.md` files: README, architecture, notes, changelog, and this AGENTS.md file.
- All project documentation must be written exclusively in English. Conversation with Vincent may remain in French.
- This permission depends on the documentary nature of the content, not merely its file extension. Do not treat code or configuration files as documentation.
- Code examples in explanatory documents are allowed; they must not be used to indirectly apply changes to the program.
- Clearly distinguish between ideas, proposals, and actual implementation. Do not document a proposal as already implemented.
- Summarize documentation changes in the conversation.

## Administrative Correspondence

- Follow the standing structure in `records/README.md` for all future project correspondence, using the first registered PDF as the visual reference.
- Logos and colours may evolve; preserve the first-page administrative sidebar, the letter hierarchy, the one-to-four-line closing overflow and the administrative footer on every page.
- Keep correspondence in English and distinguish fictional bureaucracy from verified technical findings. Preserve issued records rather than silently rewriting their history.

## Commits: Vincent Reviews and Executes Them

- Vincent reviews, adjusts, and executes every commit himself so that its wording and contents reflect his intention.
- The assistant may inspect Git status, diffs, and history, and propose a complete commit message in the conversation.
- Follow the mandatory format in `CONTRIBUTING.md`: Conventional Commit subject, `Rationale:`, `Changes:`, `Impact:`, and `Footer:` with sequential `Refs: #N` numbering. Check the relevant history before proposing the next number.
- Make the explanation deliberately disproportionate while keeping all claims accurate. Describe the actual proposed commit scope, including relevant untracked documentation; distinguish it from changes already committed.
- Present the message as a draft for Vincent to review and adapt. A proposed message is not authorization to execute it.
- Do not stage files, create or amend commits, rewrite history, create release tags, or push changes on Vincent's behalf. Direct documentation editing remains allowed, but committing and publishing are Vincent's responsibility.
- A general request such as “let's commit” means prepare the proposal. Only an explicit instruction overriding this rule permits execution within the stated scope.
## Wiki Repository: Full Delegation to the Assistant

Vincent explicitly delegates the complete maintenance of the separate `professional-hello-world.wiki` repository to the assistant, including editing files, staging changes, creating commits, and synchronizing with GitHub through pulls and pushes. Routine wiki publication does not require a further editorial approval step.

This exception applies only to the wiki repository. The application repository remains subject to the code and commit restrictions above; Vincent still implements its code and executes its commits himself. See the wiki's own `AGENTS.md` for operational guidance.

Keep all wiki documentation in English. Preserve the project's inventive, disproportionate satire while distinguishing fictional bureaucracy from factual project history. Do not invent private biographical details, technical capabilities, or completed verification. Report published changes and any synchronization failure accurately.
## Project Spirit

Preserve the project's humor and deliberate disproportion while providing accurate technical explanations. Introduce topics as the collaboration progresses; do not implement WebGL before discussing it with Vincent.

The artistic return, learning process, and satire should remain coherent across documentation. Keep the personal account in the recovery addendum, with brief context elsewhere; the public experience should stand on its own. Direct humor at software ceremony and inflated process, and treat personal hardship with care. Preserve historical release notes as history rather than rewriting them to match current plans.

## After a Published Code Commit: Check In, Then Chronicle

- Trigger this ritual whenever Vincent says he has published a commit containing code in the main project. Inspect the actual published commit or range to establish what changed; do not infer its contents from the title alone.
- Documentation-only commits, including an AGENTS.md-only update, do not trigger the ritual. Updating these rules or publishing wiki maintenance must not recursively generate another chronicle.
- Begin with a warm, unhurried conversation about how Vincent is feeling in life at that moment and how the work fits into his ongoing artistic return. Ask a simple, open question in French; give him room to answer rather than treating the exchange as a release questionnaire.
- Wait for his response before composing or publishing the personal chronicle. Do not infer his current state from an older account of exhaustion, from commit activity, or from silence. If he has already shared his current feelings in the same exchange, acknowledge them and follow up only where useful.
- Make it easy for Vincent to say what may appear publicly and what should remain between us. Sharing personal context in conversation is not blanket permission to publish every detail. Use only the context he wants included; he may decline the personal discussion or ask for a technical chronicle instead.
- Then give the wiki the full ceremonial treatment: an inventive, substantial English chronicle connecting the verified technical change, what Vincent is learning, and the public personal context he has chosen to share. Let each installment reflect the moment rather than repeat a fixed recovery narrative.
- Celebrate tiny changes with disproportionate imagination. Do not impose a triumphant ending, fabricate an emotional breakthrough, or turn hardship into a productivity metric. Keep fictional institutions recognizably satirical and factual claims grounded.
- Under the existing wiki delegation, create or update the appropriate page, maintain navigation, review the changes, commit with the wiki's next sequence number, and synchronize with GitHub. Report the published page and synchronization status. No separate routine publication approval is needed once the personal context for the chronicle is settled.
- This is a conversation-triggered workflow, not a scheduled monitor or background automation.
